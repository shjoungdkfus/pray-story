## 🔑 구글 로그인 SHA-1 등록 현황 (2026-08-05 정리 — 헷갈리기 쉬우니 반드시 참고)

### 왜 이게 중요한가

Android 네이티브 구글 로그인은 요청한 앱의 **`패키지명 + 서명 인증서 SHA-1`** 조합이 같은 GCP 프로젝트의 **Android 유형 OAuth 클라이언트**에 등록돼 있어야만 ID 토큰을 내준다.
**Play는 업로드한 AAB를 "앱 서명 키"로 재서명해서 배포한다.** 그래서 업로드 키 지문만 등록해두면 **로컬 빌드는 되는데 Play 배포본만 전원 로그인 실패**한다 — 2026-08-04~05에 실제로 겪은 S1 Blocker(PS-AUTH-05)가 정확히 이 케이스다.

### 인증서 두 종류 (절대 혼동하지 말 것)

| 구분 | SHA-1 | 어디에 쓰이나 | 출처 |
|---|---|---|---|
| **앱 서명 키** | `47:85:A6:7D:9A:A6:17:2C:F0:34:09:6E:55:19:44:AD:CF:E2:9C:39` | **Play 스토어에서 설치한 앱**(테스터·실사용자 전원) | Play Console → Google Play로 보호됨 → Play 스토어 보호 → 앱 서명 |
| **업로드 키** | `0C:2C:32:5A:9F:96:43:EB:48:7F:AB:4B:E6:B9:DB:E2:00:A3:72:BD` | **로컬 release 빌드**(`flutter build apk --release` 등) | `android/upload-keystore.jks` |
| **debug 키** | `A8:C6:35:C2:1B:69:FB:DA:18:B2:9D:2F:73:64:CB:C0:67:5D:30:C2` | **로컬 debug 빌드**(`flutter run`, `flutter build apk --debug`) | `~/.android/debug.keystore` (alias `androiddebugkey`, storepass `android`) |

> 로컬에서 확인하는 법: `keytool -list -v -keystore android/upload-keystore.jks -alias upload`
> debug: `keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android`
>
> **debug 키도 GCP에 등록돼 있다** — 2026-08-06 실기기 검증에서 debug 빌드로 구글 로그인(계정 선택→동의→세션 생성) 정상 동작 확인. 종전 이 표엔 debug 항목이 빠져 있어 "debug 빌드는 구글 로그인이 안 될 것"으로 오판할 뻔했다.

### 규칙

- **Android 클라이언트 ID는 코드에 절대 넣지 않는다.** 앱이 참조하지 않고, 구글이 "이 패키지+서명 조합이 등록됐나" 대조하는 용도로만 쓴다. 그래서 SHA-1 등록만으로 해결되고 **재빌드·재업로드·재심사가 필요 없다.**
- **웹 클라이언트 ID는 건드리지 않는다.** 코드의 `serverClientId`가 이걸 가리킨다.
- Cloud Console UI가 Android 클라이언트당 SHA-1을 1개만 받으면 **클라이언트를 여러 개 만들어 공존**시키는 게 정상 구성이다.
- 콘솔 설정 반영엔 **5분~몇 시간** 걸린다. 바로 안 된다고 다른 원인을 찾지 말 것.
- **앞으로 서명 키가 바뀌거나 앱을 새로 만들면 이 표를 먼저 갱신할 것.**

### 검증할 때 주의

> ⚠️ **`flutter install`은 재빌드를 하지 않는다.** 기존 `build/app/outputs/flutter-apk/app-debug.apk`를 그대로 설치할 뿐이라, 코드를 고친 뒤 `flutter install`만 돌리면 **옛 빌드로 검증하게 된다**(2026-08-06에 실제로 겪음 — 수정한 버튼이 화면에 없어서 "수정이 안 먹었다"고 오판할 뻔했다). 반드시 `flutter build apk --debug`(또는 `--release`)를 **먼저** 돌리고 나서 `flutter install`할 것.

Play 배포본 문제는 **반드시 Play 스토어에서 설치한 빌드로** 확인해야 한다. 로컬 빌드는 업로드 키로 서명돼 원래부터 잘 되므로 **아무것도 검증하지 못한다.** 2026-07-29에 신규 계정 `praystorytest@gmail.com`으로 로컬 빌드 로그인 테스트를 통과시킨 탓에, 이 결함을 배포 전에 잡지 못했다.

### Edge Function 배포 완료 + API 테스트로 검증 (2026-07-16 새벽)
- `npx supabase` CLI로 프로젝트 링크 후 `delete-account` 함수 배포 완료 (Docker 불필요, 그냥 됨)
- curl로 더미 계정 2개(모임장 A, 멤버 B) 만들어 실제 시나리오 재현 테스트:
  - **1차 테스트에서 버그 발견**: A(모임장) 탈퇴 시 모임 전체 + B의 편지까지 통째로 삭제됨 (B는 아무 행동 안 했는데 데이터 손실)
  - **수정**: Edge Function에 소유권 자동 이전 로직 추가 — 탈퇴하는 사용자가 방장인 모임에 다른 멤버가 있으면, 가장 먼저 들어온 멤버에게 `owner_id`/`role` 자동 이전 후 계정 삭제 진행. 멤버가 자기 혼자뿐이면 기존대로 모임째 삭제
  - **재배포 후 재테스트로 확인**: 모임 생존, B 소유권 승계, B의 편지 생존, A의 편지만 삭제(본인 것이라 정상), A 재로그인 실패(완전삭제 확인), B 셀프삭제(단독 소유자 케이스)도 정상 동작
- 테스트 스크립트는 scratchpad 임시 폴더에만 있고 저장소에는 없음(재현 필요시 새로 작성)
- Supabase 배포에 쓴 개인 액세스 토큰은 임시 파일에 잠깐 저장 후 즉시 삭제 — **사용자가 Supabase 대시보드에서 해당 토큰 revoke 권장**

### ⚠️ 계정 삭제 기능 — 나중에 실기기 테스트할 때 함께 확인할 것
API 레벨 테스트는 통과했지만, 아래는 확률은 낮아도 실기기/실사용 흐름에서 한 번 더 봐두면 좋은 것들:
1. **탈퇴 도중 네트워크가 끊기는 경우**: `delete-account` 함수 안에서 기도기록/프로필까지는 지워졌는데 마지막 `auth.admin.deleteUser()` 호출만 실패하면, 로그인은 되는데 프로필이 없는 어중간한 상태가 될 수 있음 → 이 경우 앱이 신규가입 화면으로 보내는지, 이상하게 멈추진 않는지 실기기에서 비행기 모드 전환 등으로 재현해볼 것
2. **모임 소유권 자동 승계 시 알림 없음**: 방장이 탈퇴하면 가장 먼저 들어온 멤버에게 동의 없이 방장 권한이 넘어감(데이터 보존이 우선이라 의도적으로 이렇게 처리) — 실기기에서 그 멤버 계정으로 로그인해 그룹 상세 화면이 "내가 방장"으로 정상 표시되는지, UI가 깨지지 않는지 확인. 필요하면 승계 알림 기능은 이후 세션에서 별도 추가 고려
3. **Flutter Web 빌드는 미대응**: 이 Edge Function엔 CORS 헤더가 없어서 브라우저(Flutter Web)에서 직접 호출하면 막힘 — 지금은 Android/Play스토어만 타겟이라 무관하지만, 나중에 웹 빌드를 추가하게 되면 이 함수부터 다시 손봐야 함
